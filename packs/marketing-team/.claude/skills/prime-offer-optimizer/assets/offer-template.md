# One page offer template

Use this exact structure for `Avatar/Offer.md` in the main team. Read it before you create or edit that file.

About 400 to 600 words, shorter when the offer allows it. It is a buyer facing document: it reads as one piece of writing, in the owner's voice, at about a sixth grade reading level. It is not an internal checklist, so the section labels below are scaffolding for you, not headings a buyer has to read. Keep whichever headings help the page make sense and drop the rest.

No em dashes, no en dashes. No invented prices, proof, URLs, payment links, deadlines, or guarantees.

```
# Offer: [offer name, or the plain description if it has no name]
Version [X.Y] | Built from Living Avatar v[X.Y] and MOAT v[X.Y] on [date]
Status: [WORKING DRAFT, missing: ... | READY FOR REVIEW | APPROVED by owner on [date]]

## Who it is for
[Specific Person: the problem they have, that they can pay for this, and the conditions
they need in order to benefit. Nothing irrelevant.]

## The problem and what changes
[Specific Problem in the buyer's words, then the promise as one concrete outcome.
Timeframe only if supplied, supported, or marked [PROPOSED].]

## Why this approach
[Specific Process, stated plainly: the main steps and how they lead to the outcome.
Written from the process explanation exercise, never pasted from it.]

## How it works
[What actually happens, in order, from the day they start. Delivery format goes here,
not in the section above.]

## Proof
[Relevant evidence, with the customer type, starting point, result, timeframe and
limits you have. Mark anything unverified. If proof is thin, say what exists rather
than stretching it.]

## What is included
[Deliverables. Plain list. Nothing padded.]

## Guarantee
[Only if there is a real one. The result or experience, the measurement period, the
client's responsibilities, the remedy, and the limits. Otherwise delete this section.]

## Price and terms
[Price, payment schedule, engagement period, any other charges. Never invented.
Mark any option you are proposing as [PROPOSED] with its assumptions.]

## Bonuses
[Only if one removes a real obstacle. No inflated values. Otherwise delete this section.]

## The next step
[One primary action that fits how they sell. Placeholder in brackets for any link that
does not exist yet, naming what it needs.]

---
## Version log
- v[X.Y] [date]: [what changed and why. Business terms that changed get named here.]
```

## Placeholder rules

- A missing fact is a visible placeholder in square brackets saying what is needed, for example `[FILL IN: price and payment schedule]`.
- A page with any placeholder left in it carries `Status: WORKING DRAFT` and lists what is missing on that line. Never let a draft look publish ready.
- A proposal is marked `[PROPOSED]` inline and explained in `Avatar/Offer Review.md`. A proposal never becomes an agreed term just because the next draft was written.

## Versioning

Open a new version whenever a business term changes: buyer, promise, price, scope, guarantee, or timeframe. Copy edits do not need a new version. Never overwrite an approved version; add the next one and keep the version log at the bottom.

If the owner runs more than one offer, the file is `Avatar/Offer - [offer name].md` and the offers are never blended. Say which one is primary, because Buyer Runway points at one buy now asset.
